# Synthetic ∂ss demonstration

This folder contains a small, dependency-free Python demonstration of the ∂ss decision loop.

All records in `cases.json` are fictional test data. They are not real addresses and must not be used for delivery, customer records or operational decisions.

## Run

From the repository root:

```bash
python demo/dss_demo.py
python demo/dss_demo.py --json-out demo-trace.json
python -m unittest discover -s tests -v
```

No third-party packages are required.

## What it demonstrates

- `VERIFIED`: one candidate matches all declared fields after case/whitespace normalisation.
- `CORRECTED`: one candidate is unique under the demonstration retrieval rule, and the return check passes.
- `UNRESOLVED`: no candidate, multiple candidates, or a failed return check.

The return check requires exact agreement on premise, locality and postcode, and permits at most one edit in the street field for the typo-correction example. The edit-distance helper also rejects non-text operands rather than normalising two malformed values into an apparent match. Address fields must be text: non-string values are not converted into strings, malformed case/intended/candidate containers are refused, and a malformed candidate record is not silently skipped beside a possible exact match. Non-text or blank candidate identifiers receive deterministic trace labels rather than being copied into the selected-candidate field. This is a deliberately narrow teaching rule, not a universal address-identity policy.

## Shared evidence trace

Every decision trace now carries the same evidence vocabulary used by the vehicle-event experiment:

- `SUFFICIENT_AND_CONSISTENT`: required fields are present and the return check passes.
- `INSUFFICIENT`: required information or a supported candidate is absent.
- `CONFLICTING`: a candidate is found but contradicts a protected identity field at return check.
- `AMBIGUOUS`: more than one candidate satisfies the retrieval conditions.

The original `terminal_state` and `reason_code` remain available; `reason_codes` is also emitted as a one-item list for a common trace shape. Each trace also includes a deterministic `trace_id`, the fixed `ruleset_version` (`synthetic-address-demo/1.0`) and a declared `normalisation_rule`. The trace ID is a convenience key derived from the case identifier, candidate labels/count and decision outcome; it is not a signature, content-integrity proof or production audit identifier. The vehicle experiment adds `MIXED` when missing and contradictory observations coexist.

## Candidate-by-candidate evidence

Each case trace now includes `candidate_trace`, in the same order as the supplied candidate list. Each entry records:

- A candidate label plus its zero-based position in the supplied list. Position keeps entries distinguishable even if source identifiers are duplicated; missing, blank or non-text identifiers receive a deterministic positional label. The aggregate selection also exposes the selected candidate position.
- Per-field intended and candidate values, their separately exposed normalised text values, whether both are valid nonblank text, and normalised equality. Malformed values are shown as supplied but are never coerced into address text; normalised values and equality are `null` when the corresponding input is invalid.
- Whether the street satisfies the demonstration's at-most-one-edit retrieval rule.
- Retrieval eligibility and the reason codes that admitted or refused the candidate.
- Protected-field checks for premise, locality and postcode.
- A final candidate disposition (for example `SELECTED_EXACT`, `REFUSED_RETRIEVAL`, `AMBIGUOUS` or `REFUSED_RETURN_CHECK`) with candidate-level reason codes.

The aggregate terminal decision remains separate from these candidate entries. The trace is generated by the evaluator's comparison rules; benchmark oracle labels are not used. Candidate order controls presentation order only: it does not resolve ambiguity or alter the decision. The field values in this demonstration are fictional synthetic data. The deterministic trace ID remains a convenience key, not a content hash, signature or production audit identifier.

## Independent candidate-trace audit

The command-line demonstration independently rechecks each emitted candidate trace against the original synthetic case. The audit independently reconstructs the aggregate terminal state and reason code, each candidate's disposition and reason codes, field normalisation/equality, retrieval eligibility and protected-field checks. It also checks candidate positions, trace cardinality and the aggregate selected-candidate reference. Tests deliberately alter field evidence, remove candidates, falsify dispositions and tamper with the aggregate outcome; each alteration must be detected. The CLI stops with a non-zero exit if the audit finds a mismatch.

The audit is a separate consistency check over the emitted evidence, not a cryptographic signature, an independent validation of the policy's real-world suitability, or proof of production accuracy. It deliberately does not consult benchmark oracle labels.

## Important limits

This is a reference demonstration, not a production matcher or evidence of accuracy. It does not use PAF, live address data, geocoding, postal validation or customer records. It has no production security, privacy, monitoring, resilience or integration controls. The synthetic scenarios are hand-authored and are not a representative benchmark.

A customer pilot must use an authorised, labelled dataset, a frozen baseline and pre-agreed acceptance criteria as described in [the pilot protocol](../commercial/pilot-protocol.md).
